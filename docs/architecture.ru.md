# Архитектура

[English](architecture.md) · [README](../README.ru.md) · [Дорожная карта](../ROADMAP.ru.md)

## От машинного кода до защищённого бинарника

vmkek переводит выбранные функции x86-64 в промежуточное представление (IR). На нём работают преобразования, в том числе смешанные булево-арифметические тождества (MBA), маскировка констант, непрозрачные предикаты и уплощение графа потока управления. Мутация снова выдаёт нативный код. Виртуализация кодирует функцию в байткод и добавляет в выходной файл среду исполнения. Параметры конкретной сборки можно посмотреть в JSON-отчёте. При выборе функций важны поддержка инструкций и соглашение о вызовах.

| Режим | Что покрывает |
| --- | --- |
| Нативная защита Windows PE и Linux ELF | Выбранные функции в поддерживаемых образах x86-64. Внешняя VM исполняет байткод функции. Внутренняя интерпретирует байткод выбора нативных обработчиков. |
| Лабораторная VM | Стековая, регистровая и смешанная формы. На экспериментальных глубинах 3 и 4 отдельные операции обработчиков исполняются как микропрограммы. Здесь же проверяются ограниченные буферы и версионированные описания модулей. |
| Онлайн-режим | Клиент проверяет подписи сессии и модуля перед приёмом зашифрованного байткода для совместимой VM. Часть операций исполняется на сервере. |
| Исследование драйверов Windows | Перезапись проверяется на синтетических образах PE с подсистемой Native. Загрузка, IOCTL и выгрузка на живом ядре входят в [дорожную карту](../ROADMAP.ru.md). |

## Целостность и ключи

Лабораторные профили PE и ELF при запуске проверяют подпись ECDSA P-256 и подлинность зашифрованного блока через ChaCha20-Poly1305. HKDF-SHA256 разделяет ключи по назначению и контексту сборки. Этот режим использует отдельный ключ подписи, а seed задаёт воспроизводимые различия между сборками. В стандартном детерминированном режиме CLI ключи выводятся из seed и воспроизводятся вместе со сборкой. Для проверки подлинности важны доверенный открытый ключ и доверенное окружение запуска.

Онлайн-режим использует TLS 1.3 и подписи метаданных на уровне приложения. Разрешение связывает выдачу модуля с конкретной сессией и поколением VM. При смене поколения среда исполнения учитывает активные кадры. Сервер может отозвать доступ. Операции, реализация и секреты которых должны оставаться за пределами клиента, выполняются на сервере. Тот, кто контролирует клиентский процесс, может наблюдать доступные этому процессу байткод и данные во время исполнения.

## Профили наблюдений

Названия относятся к подключаемым конфигурациям подписанных политик Lab и Online. Квалификация привязана к проверенным приложениям и стендам. Windows x64 проверен на Windows 11 `10.0.26300.9974`. Политика Windows привязывает числовой build `26300`. Linux x64 проверен в WSL2 с Ubuntu 24.04.2, glibc 2.39 и ядром `6.18.58.1-microsoft-standard-WSL2`. Политика Linux привязывает числовую версию ядра и хеш полной строки release.

| Профиль | Windows x64 | WSL2 x64 |
| --- | --- | --- |
| `observe` | Сообщает о подключении отладчика к текущему процессу и о наблюдениях в явно подписанных неизменяемых file-backed RX-диапазонах собственного PE-образа. API отладчика образуют одну зависимую группу сигналов. | Сообщает `TracerPid` лидера группы потоков в пределах видимости текущего procfs и наблюдения из явно подписанных неизменяемых file-backed RX-диапазонов собственного основного ELF-образа. |
| `supported-enforce` | Подписанные Lab и Online политики отладки проверены при запуске, позднем подключении и активных вызовах. Legacy Online stop по собственному коду проверен отдельным целевым тестом. | Подписанные Lab политики отладки и целостности основного ELF проверены на запуске под собственным GDB/LLDB и при устойчивом несовпадении подписанного диапазона. Остановка своей Online сессии проверена при запуске под собственным GDB. |
| `experimental` | Более широкая совместимость Windows, общее покрытие инструментирования и профилированная реакция Online на целостность кода за пределами целевого теста требуют квалификации. | Bare-metal Linux, внешние PID namespace, DSO, внешние профилировщики и реакция Online на целостность кода требуют квалификации. |

`observe` допускает вызовы и записывает типизированные результаты, включая недоступную выборку. В `enforce` отсутствующая, просроченная или неопределённая обязательная выборка может вернуть `Unavailable` (1). Подтверждённый свежий Stop возвращает `Denied` (3) и сохраняет ещё не опубликованный выходной буфер. Offline Stop сохраняется в течение активации. Online сначала закрывает локальный допуск, затем пытается отправить одно ограниченное сообщение о своей сессии. Подтверждение доставки не меняет локальное решение. Постоянный отзыв доступа требует отдельного административного решения.

Совместимость Windows проверена на 1 008 отдельных процессах, по 504 на режим и по 42 на сценарий в каждом режиме. Требование 24-часового soak снято после частичного прогона с 13 проверенными запусками. В WSL2 проверено по 390 строк на режим. Read-only проверка Frida 16.6.6 в WSL2 подтвердила 60 запусков собственной фикстуры. Windows матрица зафиксировала 120 пропусков и 60 неопределённых результатов при активности stock-инструмента, а также 30 обнаружений отдельного изменения собственной подписанной метки. Эти результаты квалифицируют конкретные лабораторные сценарии. Production EDR, другие сборки ОС и общее обнаружение Frida остаются открытыми.

Внешнее чтение памяти даёт доступ к данным, доступным клиенту. Приостановленный процесс выполняет проверки только после возобновления. При возобновлении допуск проверяет свежесть. Владелец ядра или гипервизора контролирует среду исполнения. Короткое событие может произойти между выборками. Независимые измерения первой попытки и переноса между сборками остаются неквалифицированными.

## Развёртывание подписанной политики и восстановление

1. Независимо подготовьте ключ проверки detection policy. Используйте API подписи для нужного профиля Offline или Online и привяжите приложение, сборку, платформу, срок действия, epoch и поддерживаемые правила. Конфигурации Online добавляют подписанный consent на локальный Stop. Windows использует наблюдаемую конфигурацию `VMKR17`, Linux использует `VMKRA10` с доступом только владельцу и отдельной учётной записью устройства.
2. Храните принятые epoch, хеш ревизии и заданный epoch floor в доверенном хранилище launcher или системы развёртывания. Offline верификация принимает предыдущую ревизию явно. Инициализация Online применяет floor из конфигурации. Система развёртывания проверяет замену внутри одного epoch перед обновлением этой конфигурации.
3. Сначала установите политику на малой группе тестовых устройств. Откройте свежие runtime handles и проверьте чистые ABI результаты, свежесть наблюдения и подтверждение Online отчёта перед расширением развёртывания.
4. Для дефектного правила подпишите исправленные или прежние рекомендованные настройки с epoch выше затронутой ревизии. Проверьте новый пакет, поднимите доверенный floor вместе с развёртыванием и инициализируйте свежие handles. Допускается побайтно совпадающий повтор текущего epoch. Другая ревизия того же epoch или прежний epoch отклоняются при передаче предыдущей ревизии.
5. После возврата транспорта установите новую разрешённую сессию. Административный отзыв требует отдельного подписанного restore до возобновления доступа. Сохраняйте политику и записи решений для аудита.

На чистом снимке исходников с Rust 1.95.0 проверьте контракт пакета и нативную Offline фикстуру canary/rollback. Фикстура использует отдельные активации собственного runtime.

```sh
cargo +1.95.0 test --locked -p vmkek-protocol --test anti_analysis_contract
cargo +1.95.0 test --locked -p vmkek-runtime --lib staged_policy_rollout_recovers_with_a_higher_epoch -- --ignored --nocapture
```

В проверенном сценарии PE CLI протектора собирается в WSL, а Windows runtime и фикстуры — в x64 MSVC. Нативная сборка отдельного Windows CLI остаётся неквалифицированной. Windows runner запускается в x64 Developer PowerShell. Linux матрица использует WSL2 или Linux x64. Для инструментов вне PATH задайте `VMKEK_A10_GDB` и `VMKEK_A10_LLDB`. Windows Response использует `VMKEK_A07_ONLINE_CONFIG` для Online строк. Linux Online строки используют `VMKEK_A10_ONLINE_CONFIG`. Для них нужен приватный loopback TLS стенд. Для каждого прогона укажите локальный каталог вывода. [Подготовка Windows](../tests/windows/README.md) · [Linux runner](../tests/linux/anti_analysis.py)

```powershell
pwsh -NoProfile -File tests/windows/anti_analysis.ps1 -Case Response -Profile enforce -Repeat 30 -OutputDir out/windows-response
```

```sh
python3 tests/linux/anti_analysis.py --case all --profile enforce --repeat 30 --output out/linux-response
```

## Что проверяем

- **Эквивалентность.** В экспериментальной сборке лабораторной VM Z3 ищет контрпримеры к отдельным 64-битным преобразованиям. Одно из проверяемых равенств `(x + a) + b = x + (a + b) mod 2^64`. Оно относится к результату линейной последовательности. Перед применением правила среда проверяет форму этой последовательности. Отдельные [проверки Kani](c5-kani.md) покрывают целочисленные тождества IR при заданных условиях на флаги.
- **Совместимость.** Дифференциальные тесты сравнивают обычное и защищённое исполнение. У живых прогонов есть конкретная платформа, набор примеров и профиль. См. [лабораторию Windows](../tests/windows/README.md) и [стенд оценки](../evaluation/README.md).
- **Криптография.** Подпись и аутентифицированное шифрование обеспечивают целостность и подлинность при соблюдении требований к ключам и проверке. Стойкость к реверсу измеряется отдельно.
- **Сопротивление анализу.** Замеряем время восстановления поведения и усилия до получения принятого результата. Повтор на другой сборке показывает, какая часть работы переносится. Вместе с результатом публикуем корпус, тайм-ауты и лимиты ресурсов.
