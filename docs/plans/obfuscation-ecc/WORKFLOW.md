# Общие правила выполнения этапов

## Исходная точка и границы

Исследовательская база — `4cd330d0ba73b6a912506c3c83c2ee1331af262d`. Исследование находится в `docs/research/obfuscation-research.ru.md`. Его ссылки C обозначают код этой версии, S/B/F — внешние источники, E — выполненные адресные проверки. Каждый этап ссылается на эти идентификаторы через исследование.

Перед разработкой записать абсолютный путь рабочей копии, HEAD, dirty status, версии инструментов и различия с исследовательской базой. Не применять `reset`, `clean` или `checkout` поверх пользовательских изменений. Если затрагиваемые файлы уже изменены, отделить исходный снимок и изменения этапа в собственной рабочей копии; не включать чужие правки в свой diff. Для нового worktree использовать ветку `codex/obfuscation-<этап>`, если проект не требует другой схемы.

После каждого этапа исходной точкой следующего становится точный принятый снимок. Сохранить `stage-base` и `candidate`: Git SHA для коммитов, а для незакоммиченных изменений — patch, список новых файлов и SHA-256 содержимого. Review сравнивает с `stage-base`, а не с произвольным `HEAD~1`. Криптографические секреты в артефакты и отчёты не включать.

Область: офлайн Windows PE и Linux ELF x86-64, user mode. Нативный протектор, authenticated-профиль и экспериментальный Lab описывать раздельно. Сервер, внешнее доверенное оборудование и драйверы ядра не входят в задачи. Исследование и его исходные evidence сохранять как исторический срез; новые результаты писать отдельно.

## Состояния и переходы

`NOT_STARTED → DEVELOPING → REVIEW_REQUIRED → IN_REVIEW`.

- Есть подтверждённые замечания любой серьёзности: `FIX_REQUIRED → FIXING → REVIEW_REQUIRED`, затем новый review.
- Нет открытых замечаний и все обязательные проверки выполнены: `COMPLETE`.
- Обязательная проверка или необходимая зависимость недоступна: `BLOCKED`, с условием продолжения. Это не `COMPLETE`.

У номера раунда нет предела, который автоматически означает успех. Если один дефект возвращается, пересмотреть причину и тест, а не повторять прежний патч. Замечание можно закрыть как ошибочное только с проверяемым обоснованием, подтверждённым review. Перенос подтверждённого дефекта в backlog не считается чистым этапом.

Итог эксперимента хранится отдельно от состояния выполнения: `ADOPT`, `REJECT`, `INCONCLUSIVE` или `NOT_APPLICABLE`. Отрицательный результат допустим и не требует искусственно добиваться «усиления». `COMPLETE + REJECT` означает завершённый эксперимент с отказом от кандидата; экспериментальное изменение не включается в основной профиль. `INCONCLUSIVE` требует явно описанного решения о дальнейшем исследовании и не даёт права заявлять стойкость. Следующий этап обязан проверить, не зависит ли он от отклонённой возможности, и записать выбранный вариант до разработки.

## Обязанности ролей

Feature dev реализует ровно один этап, записывает принятый дизайн, diff, проверки и ограничения. Его внутреннее review не заменяет отдельный `/rust-review`.

Rust review изучает полный diff этапа, новые файлы и затронутые зависимости. Кроме Rust, проверяет Python, shell, настройки стенда и claims в пределах этой задачи; при необходимости использует подходящий профиль проверки. В код не вносит исправлений. Не останавливается на перечне исправленных строк и не считает зелёный тест доказательством качества всего изменения.

Orch fix получает последний отчёт, исправляет подтверждённые дефекты по ID, добавляет регрессионное воспроизведение там, где проверяется поведение, и возвращает результат на review. Не создаёт новые возможности под видом исправления. Для неточного текста, названия или форматирования достаточно адресной проверки; бессмысленный тест ради процесса не нужен.

Повторное review проверяет закрытие прежних ID, регрессии и весь итоговый diff относительно `stage-base`. Новый дефект получает новый ID. Чистое review относится только к точному проверенному снимку; любой последующий патч требует обновить проверки и снова пройти review.

## Проверки и измерения

Сначала прочитать проектные команды CI и toolchain. Для Rust обязательны `cargo check`, `cargo fmt --check`, `cargo clippy -- -D warnings` и `cargo test` с нужными package/target/features. Записывать полные argv и exit codes. Не включать все features вслепую: экспериментальные, платформенные и несовместимые сочетания проверять отдельной матрицей. `cargo audit`, если доступен, записывать отдельно от корректности. Существующие предупреждения и failures показывать с базовым воспроизведением, не скрывать подавлением lint. Ограничить сборку `CARGO_BUILD_JOBS=4`.

Для затронутой семантики проверять результаты, память, canaries, состояние, регистры, живые флаги и побочные эффекты. Для существенного дефекта регрессионный тест должен отличать сломанный вариант от исправленного. Формальное обязательство должно описывать ширину, предпосылки и наблюдаемое состояние; timeout/unknown solver не считается proof.

Базовый сравнительный протокол исследования: исходная программа, текущая защита, кандидат и абляции; 24 функции в восьми семействах, раздельные training/holdout, seed `0x0401`–`0x040a`; бюджеты 60/600/3600 секунд и 8 ГиБ на процесс с потомками. Дополнительный реалистичный корпус учитывать отдельно. Подбор вести на training; перед holdout зафиксировать конфигурации. После использования holdout для подбора он больше не считается скрытым контролем.

Сохранять `recovered`, `timeout`, `unsupported`, `error`, `not_run` отдельно. Кандидат восстановления исполняется без доступа к оригиналу и защищённой цели. Разделять извлечённые выражения/IR и реальный binary, fresh и donor→target transfer. Измерять время/успешность восстановления, перенос, build-time, startup, runtime, память и размер. Не заменять эти метрики числом инструкций, seed или изменённых байтов. Статистику группировать по функциям/семействам, не считать seed независимыми алгоритмами.

Перед дорогостоящей серией провести короткую калибровку. Длительные запуски обязаны иметь прогресс, лимиты и сохранение результатов, но сокращённый smoke не подменяет обязательную серию. Если обязательная серия не завершена, это явно отражается в состоянии этапа.

## Артефакты каждого этапа

Создавать их при фактическом выполнении, в `docs/plans/obfuscation-ecc/runs/<NN>/`; большой корпус и бинарники допускаются вне Git с manifest и стабильным путём.

| Файл | Содержимое |
| --- | --- |
| `state.md` | Состояние, base/candidate, номер раунда, открытые ID, следующий шаг |
| `implementation.md` | Решение, изменения, границы, критерии и результаты |
| `review-01.md`, `review-02.md`, … | Независимый отчёт каждого раунда, проверенный снимок, findings и вердикт |
| `fix-01.md`, `fix-02.md`, … | ID → причина → изменение → регрессионная проверка → новый снимок |
| `checks.json` | Команды, версии, профили, время, exit codes, пути журналов, выполненные и пропущенные проверки |
| `decision.md` | Наблюдение → источник/артефакт → вывод → критерий; ADOPT/REJECT/INCONCLUSIVE/NOT_APPLICABLE |

Finding имеет ID `O<NN>-F<NNN>`, серьёзность, путь/строку, условие проявления, последствия, воспроизведение и критерий закрытия. Отчёты дописываются новым раундом, прошлые результаты не перезаписываются. Формат этих отчётов — организационный; формат существующего `evaluation` без необходимости не заменять.

## Граница полномочий

Задания предназначены для последующего запуска разработки пользователем. При выполнении соблюдать действующие инструкции проекта и команды; не подставлять вымышленные «ДА» вместо ответа на обязательную контрольную точку. Этот пакет не поручает коммитить, публиковать или объединять изменения. Если командный workflow доходит до commit gate, сохранить проверенный diff и отчёт без commit.
