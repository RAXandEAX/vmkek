# Задание для orch fix

Выполни `/orch-fix-defect` по последнему завершённому review указанного этапа. Прочитай WORKFLOW, задание этапа, state и все ещё открытые findings. Убедись, что исправляешь проверенный candidate, а последующие изменения не потеряны.

1. Составь очередь подтверждённых дефектов по ID. Начни с причин, влияющих на корректность и достоверность измерений. Для независимых исправлений сохраняй понятное соответствие ID → diff.
2. Воспроизведи поведенческий дефект регрессионной проверкой, показывающей failure на сломанном варианте. Исправь причину, затем покажи pass. Для документационного замечания используй адресную проверку утверждения/ссылки.
3. Не ослабляй oracle, лимиты, assertions и критерии ради зелёного результата. Не скрывай error/unsupported и не исключай неудобные seed/функции из отчёта.
4. Выполни затронутые проверки и обязательные gates. При изменении семантики или измеряемого binary прежние результаты, зависящие от этого изменения, пометь устаревшими и пересчитай; не переписывай старые журналы.
5. Сохрани `fix-<round>.md`: ID, причина, патч, red/green или другая проверка, команды, новый candidate и оставшиеся вопросы. Обнови state на `REVIEW_REQUIRED`, а не COMPLETE.

При несогласии с finding запиши опровержение для независимого review; самовольно не закрывай его. Если фикса нет без расширения согласованной области, запиши конкретную блокировку. Если открытых findings нет, ничего не меняй. После исправлений требуется отдельный запуск повторного Rust review. Следующий этап не начинай; commit/push не выполняй.
